# Bug Audit — 2026-11-17

Independent audit against `origin/main` at `b0eb746`. Code read only: no app code changed, no
AI calls made, no build needed. Every finding below sits in a SwiftUI view or in
`DataBackupManager.swift`, and `Package.swift` compiles neither, so **no failing test could be
written for any of them**. Each one carries its exact file and line instead.

## 1. Summary for the owner

**Bugs found: 7.** Two are serious (S1), two are medium (S2), three are minor (S3). None
crashes the app.

The top 5, in plain words:

1. **Editing an exercise can delete bodyweight sets.** Suppose you log a set as "BW" (body
   weight) and then tap **Edit** on that exercise card, or edit that session from its history
   screen. The BW sets show as "0", and the app refuses 0 as a weight. When you press Save,
   those sets are thrown away for good. If every set was bodyweight, Save stays greyed out, so
   you can't fix that session at all.
2. **A reset workout day can come back.** Say you reset a fully logged day and those
   exercises have no other history (a new program's first week, for example). The app can
   mistake that for data loss. The next time it starts fresh, it puts the deleted sets back
   from its automatic backup, and it tells you so with a "restored entries" message.
3. **Importing a backup changes your settings, even though the app says it won't.** The import
   screen says "nothing is deleted or overwritten". In fact, importing replaces your current
   injury note, medical answers and profile with whatever the backup file holds. An older file
   could quietly put back an injury note from before your shoulder trouble.
4. **Backups leave out six settings.** Your calorie, protein, carb and fat targets, your
   body-weight goal, and your usual sleep hours are never written into a backup. Restoring onto
   a new phone silently puts the app's defaults back for all six.
5. **After you reset a day, the app may falsely warn "Data loss detected".** It treats your own
   reset as lost data and tells you to export a backup.

**What to avoid until these are fixed:**
- Don't use the exercise **Edit** button, or **Edit Log** on the history screen, for any
  exercise where you logged a set as BW. Correct those sets in the set rows on the day screen
  instead. That way of logging handles BW correctly.
- Don't import an old backup file unless you are setting up a new phone. If you do import
  one, check Settings → Profile, your injury note and your nutrition targets afterwards.
- If you reset a day, log something before you next close the app completely. Logging again
  stops the reset from coming back.

## 3. Severity definitions

- **S1:** loses, corrupts or misattributes logged data, or crashes or blocks launch.
- **S2:** gives wrong or unsafe training guidance (including shoulder-risk regressions), blocks a
  core flow, or wastes paid AI calls.
- **S3:** wrong or misleading display or text that the user can recover from.
- **S4:** cosmetic.

## 4. Design concerns (deliberate, still costly)

- **Automatic backups pause after a bulk delete.** `hasSignificantDrop` refuses to write a new
  backup and doesn't update its baseline. Backups stay paused until the counts grow back. After
  a reset, every set logged meanwhile has no automatic backup. This is deliberate:
  `docs/WORKOUT_DAY_RESET_2026-09-29.md` ("a sufficiently large deliberate reset may preserve
  the pre-reset backup"). F2 and F5 come from the same guard.
- **A finished body analysis lives only in memory until you press Save.** It is held in
  `BodyAnalysisRunStore` (owned by `ContentView.swift:56`). If iOS closes the app first, the
  paid result is lost. That looks deliberate (review before saving), and I didn't find it
  documented.
- **Assisted pull-ups and dips have no "assistance" mode.** "Pull-Up (Weighted or Assisted)"
  and "Dip (Assisted or Weighted)" are progressed like added load
  (`WorkoutProgressionEngine.nextLoad`). If you log assistance-machine weight, "add load"
  means more help, not less. This is a guess: I don't know how you log these.

## 5. Checked and found sound

- Backup round trip for every field of `WeightEntry`, `SleepEntry`, `MeasurementEntry`,
  `NutritionEntry`, `FavoriteFood`, `SavedNutritionProtocol`, `ProgressPhoto`,
  `BodyAnalysisSession`, `WorkoutDay`, `WorkoutExercise`, `ExerciseWeightEntry` and
  `ExercisePerformanceLog` (including `prescribedTargetRIR`, `isSessionClosed`,
  `painReviewRaw`, `replacementName`, `preferredReplacementName`, `coachingSourceRaw` and
  `targetRIR`). The exceptions are F4 and F7.
- Backup dates lose fractional seconds, but the import de-duplication rounds the same way
  (`backupDateDedupeKey`), so re-imports don't duplicate.
- Newer-version backups are refused with a clear message, and older versions 1–9 decode.
- Storage failure: the app falls back to in-memory storage, restores the last backup, and
  stops automatic backups from overwriting the good file (`TransformApp.swift:98-120`).
- Archive vs delete: `hasAthleteHistory` (`WorkoutModels.swift:135`) keeps any program that has
  skips, substitutions, started sessions or feedback.
- `canonicalLookupKey`, ported to Python and run over all 259 catalog and alias names. Every
  key collision joined spelling variants of the same lift (singular/plural, hyphen/space,
  word order); none joined two different lifts. The required pairs press/presses, raise/raises,
  lunge/lunges, bridge/bridges, squeeze/squeezes, crunch/crunches and fly/flies all converge.
  One split exists: "Pull-Ups" vs "Pull-Up" (also Chin-/Push-/Sit-Ups), because "ups" is too
  short to stem. Program names come from the catalog, which uses the singular forms, and the
  edit sheets reuse the program name, so I found no way for a plural name to be logged.
- Set entry (`SetEntryDraft`): BW parsing, RIR bounds 0–6, the ask-for-RIR-once rule, and
  keeping typed values when a save fails.
- Progression engine: the hold / reduce-load streak, judging RIR against its target,
  load steps, and never cueing a load at or below zero.
- Working-set analysis: typo-like loads are flagged only with 3 or more sets and only on the
  high side, as documented.
- Week-1 generation: 2 parallel candidates, aborted only when none is usable; a correction
  pass is skipped on planner failures; generate buttons are guarded against double taps
  (`WorkoutView.swift:716-742`).
- Rest-over alerts: one alert per exercise card, cancelled when the exercise finishes.
- Replace: re-checks pain exclusions at commit time, rolls back on a failed save, and never
  offers more shoulder risk (except returning to an earlier choice, which is deliberate).
- Restore All Defaults resets what its dialog lists. It doesn't touch logged data.
